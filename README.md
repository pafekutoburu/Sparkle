# Sparkle — legacy Bilibili compatibility fork

This GPL-3.0 fork of [kokoryh/Sparkle](https://github.com/kokoryh/Sparkle) targets selective loading delays in the white-icon iOS Bilibili international app v3.20.1 with Surge. The fork adds a SponsorBlock integration informed by [PiliPlus](https://github.com/bggRGjQaUbCoE/PiliPlus). The user confirmed automatic SponsorBlock skipping and undo on an iPhone, but reported a loading regression after broad gzip fallback was added. After restricting fallback to airborne and Chronos responses, the user confirmed ordinary loading was normal again. Danmaku was still delayed with both helpers off and recovered when purification was disabled; leaving DmView untouched did not resolve it. ViewProgress is intercepted only while a helper is enabled, and its original danmaku/video-guide fields are preserved. The user then confirmed fast danmaku with helpers disabled but reported a Surge memory warning for the enabled Chronos script. Chronos now uses a dedicated small WebView bundle instead of loading the general JSC purification bundle; the user confirmed that the memory warning disappeared, but danmaku was still delayed at that stage. A first-chunk trace recorded a 21.7-second gap between Chronos completion and danmaku request metadata; the subsequent request/response interval was about 165 ms and response processing about 1.41 seconds. The user subsequently confirmed that setting `空降资源替换` to `0` made danmaku fast and restoring `1` made it slow again, while the new danmaku helper remained enabled. Mode `2`, which retained the original player resource but applied the previous frame/header rewrite, was also slow: the iPhone logged compressed input, identity output and a synthesized grpc-status header, followed by a roughly 20-second gap before danmaku request metadata. The rewritten response now retains its original compression flag and leaves all HTTP headers/completion metadata to Surge. On 2026-10-13, the user confirmed fast danmaku, automatic skipping and undo together with Chronos script v10 (`b164661`). The compression and header changes were applied together, so the result validates the combined fix rather than proving which change alone caused the delay. Other category policies have automated coverage but have not each been tested on the iPhone.

## Install in Surge

Module: [bilibili.sgmodule](https://raw.githubusercontent.com/pafekutoburu/Sparkle/refs/heads/master/release/surge/module/bilibili.sgmodule)

Use Surge iOS 5.9.0 or later for the JSC engine. Disable the original Bilibili module before enabling this fork. Keep MITM and its trusted certificate enabled. Start with the supplied defaults; `优化评论区加载` is disabled (`#`), `资料净化` and the new `空降助手` are enabled, and `空降助手（旧）` is disabled. The two helpers are alternatives: if both are enabled, the first matching request script is the new helper. For normal use keep `空降资源替换` at `1` and return `日志等级` to `4` after diagnosis; `0` and `2` are diagnostic values that may lack automatic skipping and undo.

Automatic skipping and undo depend on the independent helper-controlled Chronos replacement and on visible danmaku. `资料净化` can be disabled without disabling that replacement. It adds category-coloured timestamp hints and reuses that resource's existing automatic seek, clickable seek, and undo behaviour. This does not guarantee skipping when danmaku is turned off or hidden. The first uncached lookup waits for the segment service with a configured 1.5-second HTTP timeout; later chunks reuse the per-video/CID cache.

## Compatibility changes

- Restore the optional request-optimization switch, disabled by default. Ordinary video-detail/comment requests stay with the app instead of being fetched again by a script.
- Keep existing Protobuf purification, using JSC with a portable UTF-8 codec instead of requiring WebView's URL/TextEncoder/TextDecoder APIs on this path. Response bodies above 1 MiB bypass scripting rather than allocating an unbounded body in the network extension.
- Add a separate `资料净化` switch for isolating the remaining Protobuf processing if device latency persists. Chronos replacement follows the new/legacy helper switches instead of this switch; JSON processing and static rules remain available.
- Preserve the previous helper under `空降助手（旧）`. Its sponsor-only filtering, eight-second minimum and request-replay implementation remain available.
- New helper records request metadata without a network call, lets Bilibili complete its own danmaku request, then queries only the third-party segment API. Danmaku and Chronos payloads use an independent byte buffer with a bounded portable gzip fallback when native decompression fails. Ordinary feed, detail, comment and playback RPCs keep native-only decompression: if it fails, purification is skipped and the original response is passed through. This avoids applying portable decompression to every large response. It caches successes for five minutes, missing data for one minute, caps its cache, validates CID/timestamps, and preserves the original response on missing metadata, malformed data or service errors.
- The legacy module does not intercept `bilibili.community.service.dm.v1.DM/DmView`, so the original danmaku configuration is preserved. `DmSegMobile` hint injection and `ViewProgress` Chronos replacement follow the helper switches. Chronos uses its own `bilibili.chronos.js` with `engine=webview`, keeping script execution memory outside the iOS Network Extension process. The output retains the original gRPC compression flag (gzip is re-encoded only when the input frame was compressed), and no grpc-status header is synthesized. Only the Chronos field is decoded and rewritten; other ViewProgress fields retain their exact original wire bytes. With both helpers disabled, neither DmView nor ViewProgress is intercepted. When a helper is enabled, ViewProgress preserves the original dm/video-guide payload and only changes Chronos.
- The Surge module's Sparkle script URLs point to this fork. Existing third-party skin and Chronos resources remain upstream dependencies.

## New helper settings

All eleven PiliPlus category names and colours are supported: sponsor, selfpromo, exclusive_access, interaction, poi_highlight, intro, outro, preview, padding, filler and music_offtopic. Each has `auto` (automatic skip), `manual` (clickable skip), `show` (hint only) and `off` settings. The default automatically skips sponsor segments and leaves other skip categories manual; full-video labels and highlights default to hints. `最短片段时长` is measured in seconds; shorter ranges are displayed without skipping.

Point highlights can be set to `manual` for a clickable jump. `mute` and `full` actions are displayed only; they are not silently converted to skips. Overlapping automatic ranges seek to the end of their union. The server defaults to PiliPlus's `https://www.bsbsb.top`, and `空降助手策略` names an existing Surge policy for the lookup. No votes, viewed counters, submissions or other service writes are sent.

## Explicitly not ported

PiliPlus's Flutter player UI, coloured native progress bar, once-per-playback skipping, native skip controls independent of danmaku, volume muting, voting/category changes, segment submission, user statistics/identity management, tracking uploads, offline integration and YouTube port-video binding are not implemented. The module provides the agreed category/hint/skip subset, not the complete PiliPlus feature set.

## Diagnose missing hints

For delayed first danmaku, keep the new helper enabled, the old helper disabled and other settings unchanged; set `空降资源替换` to `0` and restart the app. This preserves the original ViewProgress response body and headers before decompression, while keeping the new helper's danmaku request metadata and segment lookup active. The resource script logs `[Chronos] Resource replacement disabled`. Mode `2` retains the original resource URI, MD5 and signature while exercising the same protobuf round trip and transport handling as `1`. Since script v10, both modes preserve the original gRPC compression and return only the body, without synthesizing grpc-status headers or replacing completion metadata; the old identity-frame/header behaviour is no longer used. Mode `2` logs `[Chronos] Transport diagnostic: original resource retained`. Both `0` and `2` are temporary diagnostic settings and may lack automatic skipping/undo. It still matches ViewProgress; this is a response-rewrite bypass, not a measurement of all Surge startup/buffering overhead. Compare the same video from 0:00, then restore `1`. Automatic skipping and undo may be unavailable while bypassed; these diagnostic settings are unnecessary for normal use after the confirmed v10 fix.

Update the module and set `日志等级` to `2` (INFO). Keep the new helper enabled and the old helper disabled. Restart the app with danmaku visible. The `bilibili.sponsor.request` and `.response` script logs report metadata recording, response matching, decoded danmaku counts, segment-service status/cache hits and hint injection. The helper-controlled `.chronos` script logs `[Chronos] Replacement selected` when it replaces player resources. The dedicated Chronos script logs `[Chronos] Start`/`Complete`; ordinary Protobuf scripts log `[Protobuf] Start` and `Complete` with route and execution duration; these timings exclude upstream network wait and queueing before the script starts. Errors distinguish missing request IDs, missing paired metadata, invalid frames and service failures. Logging does not include request headers or cookies; return the level to `4` after diagnosis.

For the reported `BV14GHY6fExG`, the public segment service returned a sponsor range at 433.8–501.098 seconds during investigation. Test from 7:10 through 7:16 rather than only the beginning of this video: hints are emitted at the segment start in the second six-minute danmaku chunk. Service data can change. If injection is logged but no hint appears, investigate danmaku rendering and the Chronos resource next. A reported `null.length` failure was reproduced when native gzip decompression returned null, and is now covered by fallback regression tests. The exact reason for the native decompression failure remains unknown; automatic seeking and undo were subsequently confirmed on the iPhone with v10. A clickable airborne danmaku alone does not prove the patched Chronos resource loaded; the original player also supports manual airborne interaction.

## Build and verify

```bash
npm install
npm run generate
npm run check
npm run build
npm test
```

The tests execute the published bundles in a mocked Surge environment with URL/TextEncoder/TextDecoder absent. They cover native request pass-through, response preservation on errors, original comments/unknown protobuf fields, emoji, caching, category policies, compressed frames, chunk isolation, overlapping ranges and module defaults. They do not exercise the proprietary iOS player or live third-party API.
